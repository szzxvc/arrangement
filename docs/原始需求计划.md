# 社团干活打卡系统：现成方案核查与 Codex 开发提示词

核查日期：2026 年 10 月 2 日。全文中的用户输入、日期和“今天”均按北京时间，即 UTC+8；UTC 指协调世界时。

## 一、现成方案核查

**结论：找到了相近的产品，但截至本次检索，未在其公开文档中确认有一个成品能直接覆盖全部七项要求，并原生部署到 Cloudflare Workers。** 这不是对所有软件的穷尽证明。以下比较基于官方文档和项目仓库，未逐一安装、付费试用或验证中国大陆的访问表现。

| 方案 | 类型 | 已证实的相关能力 | 与本需求的差距 | 对本项目的价值 |
| --- | --- | --- | --- | --- |
| [LibreBooking](https://github.com/LibreBooking/librebooking) | 开源 | 响应式资源预约；资源默认不能重复预约；支持记录实际签到、签出；用户组和资源权限 | 围绕资源与预约组织操作；未确认普通用户自由建私有项目、邀请成员及任何成员点击他人状态强制修改的完整流程。官方部署依赖 PHP、MySQL 或 MariaDB 等，不能直接照其部署说明搬到普通 Workers 运行环境 | 功能最接近，可参考预约、权限与签到规则。如果愿意使用传统服务器并接受不同交互，可进一步试用 |
| [Kimai](https://github.com/kimai/kimai) | 开源，另有托管服务 | 项目工时记录；开始、停止计时；通过团队限制项目可见性 | 官方说明未证实“同一项目全体成员最多一个计时者”、互斥预约及全员强制改状态的组合。团队权限需要配置；不是面向本需求的 Workers 成品 | 适合参考项目、成员与工作记录的数据组织 |
| [Skedda](https://www.skedda.com/platform/meeting-room-booking-system) | 商业在线服务 | 共享空间预约；用户组访问规则；签到及未签到释放资源 | 可将项目类比为一个容量为一的资源，但普通成员建项目、仅用户名与密码注册、全员互改状态等流程尚未确认能按要求配置；使用其网站，不是部署到自己的 Workers | 愿意调整需求时可试用的现成网站 |
| [Punctual](https://github.com/CCCrafts/punctual) | 开源 | 原生 Workers 预约应用；团队预约；通过 D1 存储约束避免重复预订 | 面向会议预约，未见本需求的干活／休息成员面板；其预约锁按五分钟分桶，不能原样满足本项目一分钟精度；目前处于 1.0 之前的版本阶段 | Workers 技术参考最贴近，适合借鉴防冲突与运行环境测试的思路 |

上述“未确认／未见”表示本次查到的资料不足以支持该能力，不等于已经证明软件无法通过配置或二次开发实现。

**我的建议：自行开发一个轻量的 Workers + D1 应用。** 本项目的定制点集中在几个短流程，直接建立准确的数据约束更容易保持交互一致。可以借鉴上述项目的思路；如复制代码，需遵守对应许可证。以下提示词按独立实现编写。

主要核查依据：

- LibreBooking 的[资源管理、重复预约与签到说明](https://librebooking.readthedocs.io/en/latest/ADMINISTRATION.html)及[仓库部署要求](https://github.com/LibreBooking/librebooking)。
- Kimai 的[开始／停止工时记录](https://www.kimai.org/documentation/timesheet.html)及[团队权限说明](https://www.kimai.org/documentation/teams.html)。
- Skedda 的[预约、访问控制与签到说明](https://www.skedda.com/platform/meeting-room-booking-system)。
- Punctual 的[仓库架构说明](https://github.com/CCCrafts/punctual)，包括五分钟分桶和数据库唯一约束。

## 二、大纲尚未规定的规则：本提示词采用的默认值

这些是开发建议，不是用户已经明确提出的附加要求；后续有新指令时应以新指令为准。

| 问题 | 默认处理 |
| --- | --- |
| 时间按什么时区？ | 固定北京时间 UTC+8，输入、显示和“今天”不受浏览器所在地影响 |
| 工作状态是否跨项目共用？ | 按项目独立；限制是每个项目最多一人干活 |
| 预约是否自动开始或结束干活？ | 不自动；实际工作状态由手动操作改变 |
| 当前时段已被他人预约，但没人干活时，能否开始？ | 可以。大纲只明确了实际干活互斥；预约作为排班记录，可提示当前预约者，但不额外禁止开始 |
| 强制把休息中的用户改成干活中时，已有别人干活怎么办？ | 拒绝，显示现有干活者；成员可先确认结束当前干活者，再单独确认开始目标用户。默认没有一步抢占操作 |
| 谁能邀请成员？ | 已加入项目的成员都可以发站内邀请；被邀请者接受后才加入 |
| 邀请方式？ | 输入完整用户名，发送站内邀请；不依赖邮箱 |
| 能否取消预约？ | 用户可以取消自己的当前或未来预约；取消不改变实际工作状态 |
| 自己预约的时间能否重叠？ | 也不能；同一项目的全部有效预约统一防重叠 |
| 两个预约首尾相接？ | 允许，例如 14:00–15:00 与 15:00–16:00 |
| 关闭页面、退出登录或预约到期后，是否自动休息？ | 不自动休息；需要结束干活或由其他成员确认强制结束 |
| 需要哪些审计记录？ | 保存实际开始／结束及操作人，强制操作必须可追溯 |

若真正想让预约保证独占，应额外明确“预约时段只允许预约人开始”“上一个人超时是否自动结束”“预约人未出现多久释放”等规则；这属于下一版需求，不应由开发模型擅自增加。

## 三、可直接交给 Codex 的完整提示词

复制本节，从“你现在负责”开始到“最终交付说明”结束，即可独立使用；前两节不必一同提供。

---

你现在负责实现一个可实际使用、可部署到 Cloudflare Workers 的“社团干活打卡系统”。请在当前工作区完成实现、数据库迁移、必要验证与部署说明，交付可运行项目。先阅读当前仓库的 AGENTS.md、已有代码与配置；如果已有项目，就沿用合理的现有结构并集成功能。若工作区为空，创建完整项目。

不要停在设计方案、界面样稿或假数据演示。下面给出的默认规则足够开展实现，常规实现选择自行决定。只有发现影响核心业务且不能由这些规则解决的矛盾时才询问用户。

### 1. 目标与技术方案

- 全中文网页，适配电脑和手机，名称暂定“社团干活打卡”。
- 前端默认采用 React + TypeScript + Vite；后端采用 TypeScript + Hono，运行在 Cloudflare Workers。
- 使用 Cloudflare D1，即托管的 SQLite 关系数据库，持久保存账号、项目、成员、邀请、工作记录和预约。
- 使用 Workers Static Assets 托管前端构建产物，与后端同域。
- 使用 Wrangler 进行本地开发、数据库迁移和部署。
- 小规模第一版采用五秒轮询同步项目页，页面隐藏时暂停轮询。数据库负责并发正确性。
- 配置与代码分离，依赖使用实际可安装且互相兼容的版本，保留锁文件。
- 如果现有仓库已经采用其他兼容 Workers 的轻量前端框架，可沿用；业务规则和验证标准保持一致。

所有下文的 API 指应用程序接口；SQL 指结构化查询语言；JSON 指用于接口交换数据的格式。日期时间固定按北京时间解释。

### 2. 必须实现的用户流程

#### 2.1 注册、登录与退出

注册与登录都只有“用户名”“密码”两个必填字段，不要求邮箱或手机号。提供密码显示开关、明确的提交结果和退出登录入口。

- 用户名支持中文、英文字母、数字和常见的下划线、连字符、点号；长度为 3–32 个字符。
- 定义一致的用户名规范化：去掉首尾空白，进行 Unicode NFKC 规范化，英文字母不区分大小写。分别保存展示名与唯一的规范化值。
- 通过数据库唯一约束处理重复用户名，包括并发注册同名的情况。
- 密码支持 8–128 个字符，支持中文与空格；不要自动 trim 密码或静默截断。
- 登录失败统一提示“用户名或密码错误”。
- 未登录时访问项目列表或项目页面，跳转登录页；登录后回到原本请求的站内路径。校验返回路径，避免跳转到外部地址。
- 刷新网页后保留有效登录。退出登录立即使当前服务端会话失效。
- 第一版无自动找回密码功能；在说明中写明这一点，不要伪造依赖未提供邮箱的重置流程。

#### 2.2 项目列表与创建

登录后首页展示“我的项目”，只包含当前用户创建或已接受邀请加入的项目。

- 有“新建项目”按钮。
- 创建表单必填名称与描述；名称 1–80 个字符、描述 1–2000 个字符，均按去掉首尾空白后的内容检查。
- 创建项目与将创建者加入成员表，必须在同一数据库事务内完成。
- 项目卡片显示名称、描述摘要、成员数、创建者及“我创建的／我加入的”标识；整个卡片可进入项目页。
- 空列表提供创建项目的明确入口。
- 全站没有公开项目列表；接口也不得把全体项目返回给前端再过滤。

#### 2.3 项目邀请

采用“输入完整用户名 → 站内邀请 → 被邀请者接受／拒绝”的流程。

- 任意已加入项目的成员都能发邀请。
- 在项目页提供邀请成员入口。
- 邀请不存在的用户名，提示“找不到该用户”；邀请已加入成员，提示“该用户已加入项目”。
- 对同一项目、同一被邀请用户，最多存在一条待处理邀请。
- 被邀请者在首页的独立“待处理邀请”区域看到项目名称与邀请者，能接受或拒绝。
- 待处理邀请不是项目成员资格；接受前不能访问项目的成员、工作状态或预约详情，该项目也不出现在“我的项目”列表中。
- 接受邀请只能由被邀请用户本人执行，邀请状态变更与加入成员表必须原子完成；重复接受不得重复添加成员。
- 拒绝后允许将来再邀请。
- 邀请功能无需邮件服务，也无需全局用户目录或模糊搜索所有账号。

#### 2.4 项目页与本人开始／结束干活

项目页展示项目名称、描述、成员列表、预约列表，并在顶部提供操作区。

每个成员只有两种工作状态：“干活中”“休息中”。这是该成员在这个项目中的状态。每个项目在任何时刻最多一个人干活；不同项目独立，不额外设置全站互斥限制。

操作区左侧是本人的“开始干活／结束干活”按钮：

- 本人在休息时显示“开始干活”。
- 点击开始时，如果项目无人干活，则创建当前用户的未结束工作记录，状态变成“干活中”，按钮变成“结束干活”。
- 如果其他人正在干活，必须拒绝，并显示“用户名 干活中，请勿同时工作”，其中用户名取自服务端当前状态。
- 即使前端已经看见别人干活，点击时仍可得到明确提示；后端始终重新核对数据库，不能只靠禁用按钮防止同时开始。
- 如果本人已经干活，重复开始应返回已有状态，不重复建立工作记录。
- 本人点击结束，只结束本人的指定当前工作记录，状态恢复“休息中”。
- 开始与结束时间使用服务端时间，不接受客户端伪造实际打卡时间。
- 成员列表显示用户名、状态图标及文字；正在干活时可附带开始时间和已持续时长。
- 关闭页面、断网、退出登录、预约开始或到期，都不自动改变实际工作状态。
- 刷新、换设备后，以服务端状态为准恢复按钮和列表。

#### 2.5 预约干活

“预约干活”按钮位于开始／结束按钮右侧。窄屏可换行，但保留操作顺序。

点击后打开弹窗或手机底部面板，分别输入开始与结束的“日期 + 小时 + 分钟”。时间精度为一分钟，采用 24 小时制。

- 用户可以建立多个预约。
- 起点不得早于服务端接收请求时的当前时间，终点必须晚于起点，最短一分钟；界面默认选择下一个可用的整分钟。
- 固定按北京时间解释输入，日期控件旁显示“北京时间”。不能直接依赖浏览器所在时区解析没有偏移量的日期字符串。
- 支持跨日预约。
- 同一项目的任何两条有效预约不得重叠，包括同一个人自己的两条预约。
- 将时间段定义为左闭右开区间 `[start, end)`：新预约 `[s, e)` 与已有预约 `[a, b)` 重叠，当且仅当 `s < b && e > a`。
- 首尾相接允许预约。完全相同、部分重叠、包含或被包含都要拒绝。
- 冲突提示提供预约者及冲突时间：“该时段已被 用户名 预约：时间段”。只向项目成员提供这些信息。
- 前端展示已预约时段，选中冲突时间后阻止提交或立即指出冲突；后端与数据库仍须防住旧页面和并发提交。
- 用户能取消自己的当前或未来预约，取消前确认；其他成员不能取消别人的预约。
- 已取消的预约立即释放时段，但保留记录供追溯。
- 预约是排班记录，不自动创建工作记录，不自动结束工作；当前有别人预约但无人实际干活时，仍允许开始，可展示当前预约者作为提示。
- 取消预约也不改变实际工作状态。

预约列表对项目全部已加入成员可见：

- 显示预约者用户名、起止时间和必要的状态标识，按开始时间升序。
- 若开始、结束都在北京时间“今天”内，显示 `14:30–16:00`。
- 其他情况显示完整日期时间，例如 `2026-10-03 14:30–2026-10-03 16:00`。
- 跨午夜必须明确显示两个日期，即使起点是今天。
- 默认展示当前和未来有效预约；过去与已取消预约放入可展开的历史区域，并提供分页。
- 用户可以明确辨认自己的预约；取消操作与该行关联。

#### 2.6 成员强制修改他人状态

每个成员都能通过点击他人的工作状态图标发起修改，必须二次确认。此能力不能仅授予创建者或管理员。

- 工作状态图标必须是可点击的按钮，附有可访问性标签，例如“修改张三的工作状态”。
- 弹窗写清目标用户名、目前状态和即将设置的状态，例如“将张三从干活中改为休息中？”。提供取消与确认两个按钮。
- 干活中 → 休息中：确认后结束目标用户的指定当前工作记录，记录操作人及 `forced` 原因。
- 休息中 → 干活中：项目无人干活时可创建目标用户的工作记录，记录实际操作人及 `forced` 原因。
- 若项目已有别人干活，强制开始也拒绝，显示“用户名 干活中，请勿同时工作”。默认不自动结束占用者、不做一步抢占。
- 用户如需交接，可以先强制结束当前干活者，再单独确认开始另一个人。
- 强制操作与普通操作共用同一互斥约束。
- 弹窗打开后状态可能已变。请求发送明确的目标状态及期望工作记录标识，不能仅发送“toggle”。期望状态已过期时返回状态冲突，刷新页面并让用户重新确认。
- 从旧页面发送的结束请求不能结束该用户随后新开始的一次工作。
- 保留操作人、被操作人、项目、原状态、新状态、实际工作记录标识和操作时间。项目成员可查看最近的操作记录。
- 取消确认弹窗时，不发修改请求。

### 3. 数据模型与并发正确性

用结构化表和迁移文件管理数据。至少包含以下实体：

| 表／实体 | 核心内容 |
| --- | --- |
| `users` | 用户标识、展示用户名、唯一规范化用户名、密码派生结果及算法参数、创建时间 |
| `sessions` | 会话令牌摘要、用户标识、到期时间及跨站请求防护所需数据 |
| `projects` | 项目标识、名称、描述、创建者、创建时间 |
| `project_members` | 项目标识、用户标识、加入时间；二者联合唯一 |
| `project_invitations` | 项目、邀请人、被邀请人、pending／accepted／rejected 状态及处理时间 |
| `work_sessions` | 项目、实际干活者、开始时间、可空结束时间、开始／结束的操作人和原因 |
| `reservations` | 项目、预约者、开始／结束时间、active／cancelled 状态、取消时间 |
| `audit_events` | 可追溯的实际状态变化，特别是强制操作 |
| 幂等请求记录 | 按用户与请求标识防止同一变更被重复执行；可采用独立表或等效存储约束 |

工作状态从 `work_sessions` 中尚未结束的记录推导，避免另外保存成员状态字段后两份数据不一致。预约的“已过期”可根据结束时间动态推导，无须定时任务改变实际工作状态。

核心数据库约束：

1. 在 `work_sessions(project_id)` 上建立仅对 `ended_at IS NULL` 生效的部分唯一索引，确保一个项目最多一条未结束工作记录。示意：

   ```sql
   CREATE UNIQUE INDEX one_active_worker_per_project
   ON work_sessions(project_id)
   WHERE ended_at IS NULL;
   ```

2. 在预约的插入和影响有效时段的更新路径设置数据库防重叠保护。推荐使用 `BEFORE INSERT` 和适当的 `BEFORE UPDATE` 触发器，检查同项目的有效预约是否满足区间重叠条件；冲突时 `RAISE(ABORT, 'RESERVATION_CONFLICT')`。更新时排除当前预约自己的标识。外键、时间顺序、有效状态也需约束。
3. 对成员关系、同名用户及同一目标的待处理邀请设置唯一约束和索引。
4. 所有 SQL 参数化绑定；数据表关联通过不可变用户标识完成，不用用户名充当外键。
5. 实际状态变更和对应审计记录必须在同一事务内提交；D1 多语句事务使用 `batch()`，不要照搬普通数据库驱动的交互式 `BEGIN/COMMIT` 代码。
6. 条件更新影响零行不代表 SQL 抛错。后续审计、成员插入等语句必须以确实成功的变更为条件，避免“主操作没生效，但后续操作仍成功”的假记录。可以使用本次操作的唯一标识关联条件；检查返回结果。
7. 实际工作结束必须限定项目、目标用户、期望的工作记录标识及未结束条件；普通结束还要限定当前登录用户。
8. 所有写入路径都共享上述约束，尤其是强制开始；并发违反唯一约束或触发器时转换成明确的业务冲突，不能只返回服务器异常。

数据库事务是保证正确性的基础。不能通过 Worker 内存变量、前端禁用按钮、事先一次普通查询或最终一致性缓存充当唯一的项目锁。

第一版直接使用 D1 主库读取业务状态，不主动引入副本读取；若已有架构启用副本，必须使用适当的一致性方式，特别是读写后的状态和权限判断。

迁移 SQL 使用明确的大写 `BEGIN`／`END` 触发器语法和统一 LF 换行，避免依赖简单按分号切割完整 SQL 文件。验证本地迁移；具备云端验证条件时，再验证远端迁移。发现 Wrangler 或远端解析差异，应按实际错误修复并保留数据库防重叠能力。

### 4. 认证与权限

- 默认使用 Workers 支持的 `node:crypto` 中的 scrypt 做密码派生；优先采用明确受支持的内置实现。
- 初始参数可取 `N=16384, r=8, p=5`，每个账号使用至少 16 字节安全随机盐，派生 64 字节结果，并合理设置 `maxmem`。保存算法、参数、盐和结果以支持今后升级。
- 使用恒定时间比较派生结果。不得保存明文密码或用一次普通摘要代替密码派生。
- 在实际 Workers 运行环境验证算法、参数、耗时和内存；说明所需套餐与资源限制。不要为了通过免费 CPU 额度而静默把密码派生降成弱参数，也不要未经测量承诺永久免费运行。
- 使用至少 32 字节随机、不透明的会话令牌；数据库保存令牌摘要。会话令牌通过 `HttpOnly`、生产环境 `Secure`、`SameSite=Lax` 的 Cookie 传递。
- 默认登录有效期七天；本地 HTTP 开发允许专用非 Secure 配置，生产环境不得沿用。
- 退出删除／撤销当前会话；服务端检查会话到期。
- 对变更接口进行来源校验并防止跨站请求伪造（CSRF）；使用会话关联防护令牌或同等可靠机制。
- 注册和登录实施后端限流，包括来源网络地址与规范化账号维度，使用持久或平台限流机制；仅依赖单个 Worker 的内存计数不足够。
- 限流发生在昂贵密码计算前，返回可理解的稍后重试提示。
- 项目读写权限在后端校验。猜到项目标识、预约标识或工作记录标识，不能获得其他项目的数据或修改权限。
- 未登录返回 401；已登录但不属于项目时，可统一返回 404，避免暴露私人项目是否存在。
- 强制修改权限只要求同项目的已加入成员；创建者在这项能力上与其他成员相同。
- 待处理邀请的读取与接受权限单独核对被邀请人。
- 对用户文本按普通文本渲染，防止跨站脚本执行；对数据库错误和服务端异常提供安全、简洁的用户提示。
- 账号密码、Cookie、会话令牌、防护令牌不能进入日志、代码仓库或前端构建环境变量。
- 私有接口返回 `Cache-Control: no-store`，避免共享缓存泄露项目数据。

### 5. 接口与响应约定

可以依现有项目风格调整路由，但至少具备下面这些语义。所有请求体使用 JSON，时间传输使用有明确单位的整数或带明确偏移量的时间字符串。

| 方法与路径 | 功能 |
| --- | --- |
| `POST /api/auth/register` | 注册 |
| `POST /api/auth/login` | 登录 |
| `POST /api/auth/logout` | 退出 |
| `GET /api/auth/me` | 获取当前用户与登录状态 |
| `GET /api/projects` | 获取本人创建／已加入的项目 |
| `POST /api/projects` | 创建项目并加入创建者 |
| `GET /api/projects/:projectId/snapshot` | 获取成员、当前工作记录、当前及近期预约等项目快照 |
| `POST /api/projects/:projectId/invitations` | 按完整用户名邀请用户 |
| `GET /api/invitations` | 获取本人待处理邀请 |
| `POST /api/invitations/:invitationId/accept` | 接受邀请 |
| `POST /api/invitations/:invitationId/reject` | 拒绝邀请 |
| `POST /api/projects/:projectId/work/start` | 本人开始干活 |
| `POST /api/projects/:projectId/work/stop` | 结束本人的指定当前工作记录 |
| `POST /api/projects/:projectId/members/:userId/work-state` | 设置指定成员的明确工作状态，带期望状态／工作记录标识 |
| `GET /api/projects/:projectId/reservations` | 按日期范围和分页获取预约 |
| `POST /api/projects/:projectId/reservations` | 创建本人预约 |
| `POST /api/projects/:projectId/reservations/:reservationId/cancel` | 取消本人预约 |
| `GET /api/projects/:projectId/activity` | 分页获取可追溯的项目操作记录 |

成功响应返回数据；错误响应有稳定错误码、中文提示及安全的必要上下文。示例：

```json
{
  "error": {
    "code": "PROJECT_BUSY",
    "message": "张三 干活中，请勿同时工作",
    "details": {
      "activeUserId": "用户标识",
      "activeUsername": "张三"
    }
  }
}
```

至少区分 `PROJECT_BUSY`、`RESERVATION_CONFLICT`、`STATE_CHANGED`、`USERNAME_TAKEN`、`VALIDATION_ERROR`、`UNAUTHENTICATED`、`INVITATION_NOT_PENDING`。业务冲突使用 409，输入不合法使用 400，限流使用 429。

变更请求携带唯一请求标识；前端对同一次操作的网络失败重试复用该标识。后端实现幂等，防止已提交但响应丢失时重复建工作记录、重复预约或重复审计。同一标识配不同参数应拒绝。幂等结果仍须校验当前登录和项目访问权限，避免绕过权限读取缓存结果。

项目快照用一次请求批量返回需要的数据，避免每个成员单独发查询。快照中的成员状态和当前工作记录应来自一致的数据库读取。

### 6. 时间处理

- 在存储层统一采用 UTC 时间戳，明确是秒还是毫秒，并统一整个项目；推荐整数秒。
- 页面输入、显示和业务日期判断固定 `Asia/Shanghai`，不是浏览器本地时区。
- 预约开始／结束必须精确到整分钟。
- 对无时区的日期控件值显式附加北京时间偏移并验证有效日期，避免运行环境默认时区以及日期溢出。
- “今天”由服务端时间和北京时间计算；项目快照提供服务端当前时间，前端可利用时间差校准显示，实际写入仍以服务端为准。
- 页面跨过北京时间午夜后，要更新预约列表的“今天”格式。
- 覆盖跨月、跨年、午夜边界及异地浏览器输入测试。

### 7. 页面和交互质量

至少完成登录／注册、我的项目、创建项目、项目详情、邀请成员、待处理邀请、预约弹窗、强制状态确认及操作记录等完整入口。

- 风格简洁，手机上不用缩放就能完成全部操作。
- 主操作醒目；成员状态同时用文字与图标表达，不能只靠颜色。
- 桌面端成员区与预约区可并排，手机端纵向排列。
- 使用容易点击的按钮和状态图标，主要触控区域建议至少 44×44 像素。
- 在窄屏上没有整页横向溢出；长用户名、长项目描述、跨日预约都能正确换行。
- 弹窗支持取消、键盘操作、焦点管理；取消不产生服务端修改。
- 所有异步操作显示提交中、成功或失败；避免重复提交。业务状态在服务端确认成功后更新，失败时不留下错误状态。
- 每次操作成功立即刷新项目快照；页面恢复可见、窗口重新获得焦点或网络恢复时立即同步。
- 页面显示期间每五秒轮询一次；隐藏时暂停，不对全站每个项目持续轮询。
- 避免多个轮询请求重叠；旧响应不能覆盖较新的操作结果。可使用请求序号、取消旧请求或服务端版本控制。
- 离线或同步失败时展示简洁的“暂时无法同步”提示，并避免用户误以为变更成功。
- 非成员项目页面显示友好的不可访问提示。
- 用户界面只显示与干活、预约、成员协作有关的内容；开发配置放入说明文件。

### 8. Workers 配置、运行与文档

- 提供实际可用的 `wrangler.jsonc` 或 `wrangler.toml`，声明 D1 绑定、前端静态文件位置和 Worker 入口。
- 使用经过核对的兼容日期；按当前运行环境需要配置 Node.js 兼容能力。
- 正确区分 `/api/*` 与前端页面路由，配置静态资源和单页应用刷新回退。
- `/api/*` 优先交给 Worker。未知接口返回 JSON 错误，不能被前端回退成 `index.html`。
- 提供 `npm install`、本地数据库迁移、开发运行、类型检查、测试、生产构建与部署命令。
- 开发与生产数据库明确区分，迁移文件进入版本控制。
- 示例配置使用明显占位值；真实数据库标识由用户创建资源后填写，不能虚构已存在的资源。

- 种子数据仅用于本地开发，不能自动在生产创建默认密码账号。
- README 写清功能、默认规则、目录结构、初始化 D1、迁移、密钥配置、部署、验证和常见问题。

- 若当前环境没有 Cloudflare 账号、网络或部署权限，完成可完成的本地实现与验证，明确列出未验证项及具体命令。没有实际成功结果时，不得声称已部署。

### 9. 必须完成的验证

核心并发、权限和时间规则需要实际测试；采用 Vitest 与 Workers／Miniflare 测试环境以及少量浏览器流程验证。数据库测试必须执行真实迁移并走真实 D1 绑定，不能仅用模拟对象证明约束成立。

| 类别 | 必须验证的场景和结果 |
| --- | --- |
| 注册 | 正常注册与登录；错误密码；规范化后同名；并发注册同名只有一个成功 |
| 会话 | 刷新有效；退出失效；过期拒绝；未登录不能读写项目 |
| 项目隔离 | 用户只见本人创建／已加入的项目；猜其他项目与预约标识不能读写 |
| 邀请 | 未接受前无成员权限；只有被邀请人能接受；重复／并发接受只加入一次；邀请失败不产生成员 |
| 并发开始 | 至少 20 个已加入成员并发开始同一项目，最终只有一条未结束工作记录，其余得到合理结果 |
| 跨项目 | 两个不同项目独立开始，不被错误的全局锁阻止 |
| 重复请求 | 开始、结束、预约及强制修改在响应丢失后重试，不重复创建记录或审计 |
| 结束 | 本人结束成功；普通接口不能结束他人；旧工作记录的结束请求不能结束新的工作记录 |
| 强制修改 | 任意成员可确认强制结束或空闲时强制开始；取消无变更；已有干活者时强制开始失败 |
| 状态过期 | 确认框打开后状态变化，旧确认请求返回冲突并刷新；不进行意外切换 |
| 混合并发 | 普通开始与强制开始同时提交，仍最多一人干活；强制结束与普通结束不重复审计 |
| 预约重叠 | 完全相同、左侧交叠、右侧交叠、包含及被包含全部拒绝；本人预约也防重叠 |
| 预约边界 | 首尾相接允许；零长度、反向区间、过去起点及非整分钟拒绝 |
| 并发预约 | 多名成员同时提交同一空闲区间，只有一个成功；数据库没有重叠有效预约 |
| 取消 | 本人取消后可以重新预约；其他人不能取消；取消与创建并发时结果符合事务提交顺序 |
| 预约与工作 | 预约开始／到期／取消不自动改工作状态；无实际干活者时按默认规则可手动开始 |
| 时间显示 | 北京时间今天简写；其他日期完整；跨午夜、跨月、跨年正确；浏览器处于其他时区仍正确 |
| 数据持久 | 重启本地 Worker 后账号、成员、预约和干活状态都保留 |
| 安全 | 变更接口拒绝缺少必要防护的跨站请求；限流有效；用户文本不能执行脚本 |
| 事务完整 | 主变更失败或条件更新零行时，不留下假审计、半加入成员或半取消预约 |
| 路由 | 项目深链接刷新可打开；未知 `/api/*` 返回 JSON；私有数据不进入共享缓存 |
| 响应式 | 至少检查 360、390、768、1440 像素视口；核心操作可完成，长文本和弹窗无溢出 |

并发测试结束后直接查询数据库验证不变量。若允许修改预约的时段或状态，还必须验证这些更新不会绕过防重叠约束。

### 10. 实施顺序和最终交付说明

按以下顺序完成：

1. 阅读仓库，确认技术方案和默认规则，建立最小可运行的 Workers + 前端 + D1 结构。
2. 完成迁移、账号会话、项目权限、创建项目和邀请流程。
3. 完成实际干活的互斥开始／结束与强制操作；先验证并发正确性。
4. 完成一分钟精度预约、防重叠、取消和时间格式；验证边界与并发。
5. 完成电脑／手机界面、轮询同步、错误与确认交互。
6. 完成必要验证、构建及 README，修复发现的问题。

完成后用简短说明交付：

- 实现了哪些完整功能。

交付标准：真实账号能登录，项目隔离有效，多用户并发仍满足每项目单人干活，预约互不重叠，成员能经确认强制改状态，数据重启后保留，手机和电脑都能完成完整流程。

## 四、技术依据与使用说明

以上数据模型、交互默认值和实施方案属于针对本需求的设计建议，软件能力与平台行为分别依据以下资料。交给 Codex 时，建议让其再次核对实施时的官方文档与依赖版本。

- [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)与[单页应用路由](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/)：用于同域托管前端，以及正确分流接口和页面请求。
- [D1 Database](https://developers.cloudflare.com/d1/worker-api/d1-database/)：`batch()` 的事务回滚语义；未使用 Sessions API 时，查询继续由主库执行。会话的一致性不能代替写入约束。
- [D1 SQL 支持说明](https://developers.cloudflare.com/d1/sql-api/sql-statements/)：D1 使用 SQLite 查询引擎，支持其大部分 SQL 约定；具体迁移仍须实测。
- [Workers 的 node:crypto 支持](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/)：截至本次核查，内置 Argon2 仍是例外项，因此此提示词选择内置 scrypt。
- [开放全球应用安全项目（OWASP）的密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)：所选 scrypt 参数是其列出的参数组合之一，仍需结合 Workers 的[资源限制](https://developers.cloudflare.com/workers/platform/limits/)进行测量。
- [Wrangler 触发器大小写问题记录](https://github.com/cloudflare/workers-sdk/issues/15314)及[迁移换行问题记录](https://github.com/cloudflare/workers-sdk/issues/14991)：作为迁移兼容性的核查线索，不假定这些问题在所有版本都仍然存在。

使用时可附上一句：“请按此文件第三节完整实现，不只生成计划；第一、二节作为选型背景与默认规则解释。”如果要让预约时段真正独占，应先修改第二节及第三节对应规则，再开始实现。
